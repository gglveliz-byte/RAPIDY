# Auditoría `/driver` — Repartidor

**Fecha:** 2026-11-13  
**Commit auditado:** `27d231e`  
**Ruta:** `/driver` — home del repartidor, con el ciclo de login/sesión `/login` y el logout de `/driver/profile`  
**Método:** auditoría estática de página, hooks, procedimientos tRPC, cookies, SSE, esquema e integración con Cliente y Negocio. No se modificó código, no se ejecutaron migraciones y no se reinició el servidor de `localhost:3000`.  
**Resultado:** 24 hallazgos — 1 P0, 11 P1 y 12 P2.

> El home **no renderiza un mapa**: el mapa operativo vive en `/driver/order/:id`. Esta auditoría revisa la cadena de ubicación completa porque el home es el único punto que la alimenta.

## 2. Flujo end-to-end (UI → hook → tRPC → DB/SSE)

```text
/login (teléfono + contraseña)
  ├─ login.login
  │   ├─ normaliza teléfono y compara bcrypt contra drivers.passwordHash
  │   ├─ setDriverCookies → quickgo_driver_token (24 h) + quickgo_driver_refresh (30 d)
  │   └─ devuelve { role: "driver", user }
  ├─ Login.tsx: setRoleUser("driver") + setSession("driver")
  └─ navigate("/driver")

/driver
  ├─ SessionGuard role="driver"
  │   ├─ login.checkAuth (cookie-first, sin exigir qs_session)
  │   └─ rehidrata driver_user + qs_session antes de renderizar
  ├─ useDriverSession → driverId desde localStorage
  ├─ order.getAvailableForDriver (polling 15 s)
  ├─ driver.getById + driver.getEarnings (solo para stats del home)
  ├─ useDriverEvents → SSE /api/events/driver/:driverId
  ├─ navigator.geolocation.watchPosition → driver.updateLocation cada ~15 s
  └─ driver.acceptOrder
       ├─ SELECT orders ... FOR UPDATE
       ├─ valida driverId nulo y estado preparing/ready_for_pickup
       ├─ UPDATE orders.driverId + status = "ready_for_pickup"
       ├─ UPDATE drivers.status = "busy" + historial
       ├─ emit order:{id} status_update + driver:{id} order_assigned
       └─ navigate("/driver/order/:id")

/driver/order/:id
  ├─ order.getById (solo si order.driverId === ctx.driver.id)
  ├─ checklist por comercio → driver.markCommercePickup
  │   └─ al completar todos: orders.status = picked_up
  └─ order.updateStatus picked_up → on_the_way → delivered
      └─ delivered: deliveredAt + driver_earnings (fee * commissionRate)
```

**Desvío principal respecto al contrato:** la aceptación debería llevar el pedido a `driver_assigned` (`contracts/orderStatus.ts:234-235`), pero el backend lo deja en `ready_for_pickup` (`server/driver-router.ts:257-260`). En el flujo de auto-aceptación, el cliente y el negocio no ven la asignación como estado; el negocio tampoco recibe evento de asignación. La asignación manual del admin sí usa `driver_assigned` (`server/admin/orders-router.ts:344-351`).

## 5. Lo que funciona y no se debe romper

- **Guard cookie-first del driver.** `SessionGuard` verifica `login.checkAuth` contra la cookie HttpOnly, rehidrata `driver_user` y `qs_session` y no exige el marcador local; un fallo de red muestra reintento y no borra la sesión (`src/components/SessionGuard.tsx:100-131,137-161`).
- **Logout y 401 role-scoped.** `DriverProfile` usa `login.logout { scope: "driver" }` (`src/pages/driver/DriverProfile.tsx:89`); el servidor solo limpia cookies driver (`server/login-router.ts:229-246`); `roleForPath("/driver/...")` devuelve driver y `clearSession("driver")` solo toca el marcador si es de driver (`src/hooks/useSessionSync.ts:55-68,107`; `src/providers/trpc.tsx:18-39`). Un 401/logout del driver no cierra customer/merchant ni vacía el carrito.
- **Identidad derivada del backend.** `acceptOrder`, `markCommercePickup`, `updateStatus`, `updateLocation`, `updateProfile`, `getEarnings` y `getActiveOrders` comparan contra `ctx.driver.id`; `acceptOrder` y `markCommercePickup` ignoran el `driverId` opcional del input (`server/driver-router.ts:73-75,93-95,117-119,138-150,219-223,284-288`; `server/order-router.ts:769-774`). No se encontró IDOR en estas procedures.
- **Aceptación serializada del mismo pedido.** `FOR UPDATE` + `order.driverId` nulo + chequeo de pedido activo evitan que dos drivers acepten el mismo pedido (`server/driver-router.ts:225-252`). El problema es la carrera entre pedidos distintos (DRV-HOME-11), no la doble aceptación del mismo.
- **Disponibilidad correcta en el backend.** `getAvailableForDriver` solo lista `ready_for_pickup` sin driver (`server/order-router.ts:691-696`) y `markReady` solo hace global ready cuando todos los comercios están listos (`server/lib/order-ready.ts:120-151`). Mantener ese filtro.
- **Retiro por comercio.** `markCommercePickup` valida asignación, estado `ready_for_pickup` del comercio, evita duplicados y solo pasa el global a `picked_up` cuando todos están recogidos (`server/driver-router.ts:284-366`). Mantener el checklist del detalle.
- **Entrega y dinero.** Al entregar se escribe `deliveredAt`, se crea `driver_earnings` con la tasa del driver y el índice único `(orderId, type)` evita duplicados (`server/order-router.ts:777-823`; `db/schema.ts:289-291`). No cambiar la fuente de `delivered_at`.
- **SSE autenticado.** `order:{id}` autoriza al cliente dueño, driver asignado, comercio participante o admin (`server/boot.ts:123-166`); `driver:{id}` exige admin o el mismo driver (`server/boot.ts:238-246`). Mantener esas comprobaciones al corregir la ubicación.
- **Privacidad del driver hacia el cliente.** `order.getById` oculta teléfono y GPS del driver en estados terminales (`server/order-router.ts:565-573`; `server/lib/order-access.ts:151-170`). Mantener la máscara.
- **Proyección sin comprobante.** `paymentReceipt` se elimina de las respuestas de pedido (`server/order-router.ts:217-223`); `getAvailableForDriver` no selecciona el comprobante. Mantener esa exclusión.
